# custom_incremental_scd2

A custom dbt materialization that standardizes **SCD Type 2 delete+reinsert**
behavior for dimension tables that use window functions (e.g. `LEAD()`) to
compute effective date ranges.

Change detection is **hash-based** — a SHA2 fingerprint of tracked business
attributes is compared between source and target, removing any dependency on
Fivetran or ingestion-tool-specific timestamp columns.

---

## The Problem

Standard dbt `incremental` materializations append new rows. This breaks SCD2
dimensions that derive `valid_to` using `LEAD()`:

```sql
LEAD(valid_from) OVER (PARTITION BY customer_id ORDER BY valid_from) AS valid_to
```

When a new version is appended, the **previous row's `valid_to` remains NULL**
(open-ended) instead of closing at the new version's start. Fixing it requires
reprocessing the full partition — which is exactly what this materialization does.

---

## How It Works

The materialization determines execution behaviour from the **state of the target
table** at run time. There are three states:

### State 1 — Target does not exist (or `--full-refresh` without `safe_mode`)

Creates the target table directly from the full model SQL. No temp table, no
validation. Standard dbt first-run behaviour.

### State 2 — Target exists and is empty (initial population)

Used when a pre-created target table has no rows yet — for example, a DDL was
applied manually before the first load.

| Step | What happens |
|------|-------------|
| 1 | Build a **zero-row probe temp** to register generated column names in `INFORMATION_SCHEMA`. |
| 2 | **Column validation** — every column the model produces must exist in the target. Hard error if not. Key columns (`target_bk_col`, `Hashbytes`, `CurrentFlagYN`) must be present in both. |
| 3 | Build **full temp table** — all model rows, no filter. |
| 4 | **INSERT** all rows into target using explicit column list. No DELETE needed — table is empty. |
| 5 | Drop the temp table. |

PK existence check is **skipped** — there is nothing in the target to compare against.

### State 3 — Target exists and has data (incremental update)

| Step | What happens |
|------|-------------|
| 1 | Build a **zero-row probe temp** to register generated column names. |
| 2 | **Column validation** — same schema contract check as State 2. |
| 3 | **PK existence check** (`strict_pk_check = true`, default) — every business key in the model output must already exist in the target. Hard error listing unexpected PKs. Protects shared tables in development. |
| 4 | Build **filtered temp table** — model SQL filtered to changed PKs only (hash comparison). |
| 5 | **DELETE** all target rows whose PK appears in the temp table. |
| 6 | **INSERT** fresh rows from the temp table using explicit column list. |
| 7 | Drop the temp table. |

## Column Naming Convention

Column names in generated models follow two deterministic rules defined in
`scd2_conventions.yml` — **not copied from any existing table in the database**.

### Source-derived columns
OpenMetadata returns Snowflake column names in ALL CAPS. The generator applies
a PascalCase transform:

```
ALL_CAPS_NAME → split on underscore → title-case each word → apply acronym list
FIRST_NAME    → FirstName
CUSTOMER_ID   → CustomerId
```

Acronyms defined in `scd2_conventions.yml.pascal_acronyms` are preserved
uppercase: `PK`, `BK`, `FK`, `ID`, `YN`, etc.

Columns with excluded prefixes (`_FIVETRAN_*`, `_DBT_*`) are stripped from
business attribute lists and never included in `hash_cols`.

### SCD2 system columns
These columns do not exist in the source — they are generated by the
materialization. Their names come exclusively from `scd2_conventions.yml`:

| Convention key | Current value | Role |
|---|---|---|
| `surrogate_pk_suffix` | `HashPK` | Surrogate PK per version |
| `surrogate_bk_suffix` | `HashBK` | Surrogate BK stable across versions |
| `source_bk_suffix` | `BK` | Original natural key (pre-hash) |
| `hashbytes_col` | `Hashbytes` | Change detection hash |
| `valid_from_col` | `EffectiveStartDateTime` | Version start |
| `valid_to_col` | `EffectiveEndDateTime` | Version end (sentinel for current) |
| `valid_to_sentinel` | `9999-12-31 18:59:59.999 -0500` | Open-end marker |
| `current_flag_col` | `CurrentFlagYN` | 'Y' = active, 'N' = historical |

Changing a value in `scd2_conventions.yml` changes the generated column name
for **all models** on the next generation pass. Existing target tables must
be migrated before running the new model.

## Configuration

Pass all custom keys inside `meta{}` to avoid dbt deprecation warnings.
Column names in `meta{}` must match the model's SELECT aliases exactly —
both are derived from `scd2_conventions.yml`, not from any existing table.

```sql
{{ config(
    materialized  = 'incremental_scd2',
    safe_mode     = true,              -- never drop existing table; always go incremental
    meta = {
        -- Required
        'source_ns':        'bronze_erp',
        'source_tbl':       'customers',
        'source_bk_col':    'customer_id',
        'target_bk_col':    'SourceCustomerBK',   -- from scd2_conventions.yml: source_bk_suffix
        'hash_cols':        ['first_name', 'last_name', 'email', 'phone'],

        -- Optional (defaults from scd2_conventions.yml)
        'is_current_col':   'CurrentFlagYN',      -- current_flag_col
        'is_current_value': 'Y',                  -- current_flag_true
        'hashbytes_col':    'Hashbytes'            -- hashbytes_col
    }
) }}
```

### safe_mode

When `safe_mode = true` and the target table already exists, the materialization
**always takes the incremental path** — even if `--full-refresh` is passed.
The existing table is never dropped. Use this when loading into a pre-existing
dimension table that must be preserved.

### Column validation

Before any data operation in incremental mode, the materialization runs two
validation steps. No DELETE or INSERT executes unless both pass.

**Step 1 — Column existence check:**

| Rule | Behaviour |
|---|---|
| Key columns (`target_bk_col`, `hashbytes_col`, `is_current_col`) must exist in both model output and target | Hard error — run stops |
| All columns produced by the model must exist in the target | Hard error — run stops |
| Extra columns in the target not produced by the model | Allowed — skipped silently |

**Step 2 — PK existence check (`meta.strict_pk_check`, default: `true`):**

| Rule | Behaviour |
|---|---|
| Every business key in the model output must already exist in the target | Hard error — run stops, no data changed |
| A PK appears in model output that is not in target | Hard error listing the unexpected PKs |

This is the primary development-time safety guard. It prevents unintended inserts
into shared target tables when other teams are working against the same data.
The run stops completely before touching a single row.

To allow new PKs (e.g. onboarding new customers in production), set:
```sql
meta = { ..., 'strict_pk_check': false }
```

### Required columns in the model SELECT

| Column | Type | Description |
|--------|------|-------------|
| `{Entity}HashPK` | VARCHAR | Surrogate PK — SHA2(BK \|\| EffectiveStartDateTime). Unique per version. |
| `{Entity}HashBK` | VARCHAR | Surrogate BK — SHA2(BK). Stable across versions. |
| `Source{Entity}BK` | VARCHAR | Original natural key from the source system. |
| `Hashbytes` | VARCHAR | SHA2 of tracked business attributes. Must match `meta.hash_cols`. |
| `EffectiveStartDateTime` | TIMESTAMP | When this version became active. |
| `EffectiveEndDateTime` | TIMESTAMP_TZ | End of validity. Sentinel value for current row. |
| `CurrentFlagYN` | VARCHAR | 'Y' = active version, 'N' = historical. |

> **Important:** The `Hashbytes` expression in the model SELECT must hash the
> same source columns, in the same order, as `meta.hash_cols`. A mismatch
> causes the materialization to detect false changes on every run.

## Source

Each dimension model reads from the Snowflake Bronze layer. The source is
registered in `models/<domain>/sources.yml` and referenced in the model via
`{{ source('source_ns', 'source_tbl') }}`.

Column descriptions, PII classifications, and criticality tags are sourced
from OpenMetadata (if connected) and reflected in `models/<domain>/schema.yml`.

## Local Development Setup

### Prerequisites

- Python 3.12
- A Snowflake account with access to your target database

### 1 — Create and activate the virtual environment

```powershell
py -3.12 -m venv C:\Users\<you>\dbt-env
C:\Users\<you>\dbt-env\Scripts\Activate.ps1
pip install dbt-snowflake
dbt --version   # confirm: Core 1.11.x, snowflake 1.11.x
```

### 2 — Configure credentials

```powershell
copy .env.example .env
```

Edit `.env` with your Snowflake credentials. Never commit `.env`.

### 3 — Load environment variables and run

```powershell
# Load .env into the session
. .\load_env.ps1

# Verify connection
dbt debug --profiles-dir .

# Full refresh (first run)
dbt run --full-refresh --profiles-dir .

# Subsequent incremental runs
dbt run --profiles-dir .
```

> There is no `dbt seed` step. The source data lives in your Snowflake Bronze
> layer, ingested by your pipeline tool of choice.

## Querying the Dimension

Intervals are **fully closed**: `[valid_from, valid_to]`.
`valid_to` is set to 1 millisecond before the next version's `valid_from`, so
no two rows for the same customer share a boundary point. The current (active)
row uses the sentinel value `9999-12-31 18:59:59.999 -0500` instead of NULL —
this means all queries can use plain `BETWEEN` without a NULL guard.

**Get the current version of every customer:**

```sql
SELECT *
FROM dim_customer_scd2
WHERE CurrentFlagYN = 'Y'
```

**Point-in-time lookup (as-of a specific timestamp):**

```sql
-- Sentinel EffectiveEndDateTime means BETWEEN works for all rows including current
SELECT *
FROM dim_customer_scd2
WHERE '2024-05-01'::TIMESTAMP_TZ BETWEEN EffectiveStartDateTime AND EffectiveEndDateTime
```

**Join a fact table to the dimension at event time:**

```sql
SELECT
    f.*,
    d.FirstName,
    d.LastName,
    d.Email
FROM fact_orders f
JOIN dim_customer_scd2 d
  ON  f.customer_id = d.SourceCustomerBK
  AND f.order_ts BETWEEN d.EffectiveStartDateTime AND d.EffectiveEndDateTime
```

> **Note:** The 1 ms guard assumes source `updated_at` timestamps for different
> versions of the same customer are always at least 1 ms apart. In practice,
> source system updates are seconds to minutes apart, so this assumption holds safely.

## Known Gaps

### SP column rename logic not registered in OpenMetadata lineage

**Root cause:**
When a pre-existing target dimension table was originally populated by a stored
procedure, that SP may have contained its own column rename decisions. That logic
is typically never registered as column-level lineage in OpenMetadata — it exists
only inside the SP code.

As a result, the SP's output column names may differ from what the metadata-driven
PascalCase transform produces from the source column names. For example:

| Source column | SP might output | This framework outputs | Gap |
|---|---|---|---|
| `EMAIL` | `EmailAddress` | `Email` | SP added suffix |
| `PHONE` | `PhoneNumber` | `Phone` | SP added suffix |
| `CREATED_AT` | `CreatedDateTime` | `CreatedAt` | SP changed suffix |
| `UPDATED_AT` | `ModifiedDateTime` | `UpdatedAt` | SP renamed entirely |

Both the existing table and this framework are internally consistent. The gap is
that the transformation mapping was never catalogued — it is a governance debt,
not a logic error in either system.

**Impact on development testing:**
If the dev target table DDL was hand-built from an existing SP-generated table,
it will inherit the SP's column names. The column validation step will fail until
the target DDL is aligned with what the model produces. Use `ALTER TABLE ... ADD COLUMN`
for any columns missing from the target DDL.

Column order in the target table does not affect correctness — `scd2_insert_fresh`
uses a named column list derived from the temp table, not positional `SELECT *`.

**Long-term resolution:**
Register column-level lineage in OpenMetadata between the source table and the
target dimension to capture SP rename decisions. Once registered, the metadata-driven
generator can read the mapping and produce target-aligned column names automatically.
